# Enterprise filtering gap assessment

Assessed 2026-09-07 against this working tree and the companion platform at
`../go-emailservice-ads`. This assesses MailScript's filtering and integration
surface, not certification of an entire deployment. Platform features below
were inspected in source; their production configuration was not qualified here.

## Diversion and screening: implemented

These are real Starlark actions supported by the native SMTP delivery path:

```python
def evaluate():
    divert_to("administrative-review@example.com")
    return
```

Diversion replaces **all envelope recipients** with the diversion destinations.
The original recipients receive no delivery from this transaction. `redirect()`
has the same envelope behavior. Repeated diversion calls collect destinations.

```python
def evaluate():
    screen_to("monitoring@example.com")
    return
```

Screening retains the original envelope recipients and adds the monitor. It is
an envelope BCC: MailScript does not add a `Bcc` header or modify `To`/`Cc` to
reveal the monitor. It forwards the same processed message bytes to the backend.
Repeated identical destination strings are deduplicated. Combining diversion
and screening sends to diversion destinations plus monitors.

Actions accumulate; they do not terminate evaluation. Use `return` to stop.
A later reject/defer still blocks delivery. These actions currently apply to
the whole transaction, not individually selected original recipients.

If any required backend recipient refuses RCPT, MailScript closes the transaction
before DATA, avoiding a delivered original with a missing required monitoring
copy. Mixed RCPT acceptance returns a temporary failure. An all-recipient
permanent refusal may return a permanent failure. Ordinary SMTP cannot guarantee
exactly-once delivery after an ambiguous connection failure; durable deduplication
requires a host adapter. A successful SMTP handoff is not proof of long-term
preservation in the monitoring mailbox.

The privacy guarantee concerns headers generated by MailScript, not backend
trace headers, access to server logs, mailbox forwarding, or subsequent DSNs.
Existing message headers are preserved, including an incoming `Bcc` if present.
Downstream deployment must control monitoring mailbox access and notifications.

With `--delivery-adapter`, the host owns the entire delivery plan and must
advertise and implement these semantics. Evaluation-only API callers must apply
the returned actions. Neither mode silently implements host behavior for callers.

Regression evidence: `cmd/mailscript/compliance_routing_test.go` evaluates the
actual Starlark primitives and checks SMTP recipients, identical DATA, duplicate
monitors, combined actions, and refusal of required destinations.

## Headers and MIME: current capability

| Operation | Current support |
|---|---|
| Inspect top-level headers, duplicates, names and values | `get_header`, `get_headers`, `all_headers`, `header_names`, `header_count`, `has_header` |
| Add a top-level header | `add_header(name, value)` |
| Remove all occurrences of a top-level header | `remove_header(name)` |
| Replace a top-level header's value | Remove it, then add its replacement; no dedicated `set_header` |
| Inspect MIME content | `mime_parts`, `get_attachments`, `get_text_body`, `get_html_body`, `get_body`, type/size/hash helpers |
| Read arbitrary nested part headers or every MIME parameter | Missing; current part view exposes selected metadata only |
| Change/remove an individual part header or MIME parameter | Missing |
| Remove an attachment, replace a part body, insert a disclaimer | Missing |
| Re-encode bodies after charset/transfer-encoding edits | Missing |
| Rewrite nested multipart or attached messages safely | Missing |

For example, replacing a top-level field works today:

```python
remove_header("X-Classification")
add_header("X-Classification", "Internal")
```

Edits are deferred until delivery serialization. Header getters and authentication
checks continue to see the original message during evaluation. Added headers
are stored in a map: repeated additions with the same exact spelling overwrite
each other; differently cased spellings can create duplicates. Removals are
applied before additions regardless of call order. This is not yet a complete
ordered, duplicate-aware editing API.

Changing a top-level `Content-Type` string is possible, but does not rewrite MIME
boundaries or transcode content. Changing an encoding label alone can corrupt
interpretation. A structured MIME mutation API must handle both metadata and bytes.
The parser currently tolerates malformed/truncated content and stops at its
depth limit; scripts lack a complete parse-status/coverage primitive to require
that every part was inspected. It does not recursively inspect attached
`message/rfc822` bodies as independent messages.

## Priority gaps and proposed Starlark surface

All names in this table are **proposed**, not registered builtins. Implement these
as host-provided Starlark functions/objects with ordinary Starlark control flow;
no language fork is necessary. Secrets and grants belong in host configuration.
Scripts request authorized operations; they must not grant themselves access.

| Priority | Gap | Proposed surface and completion criteria |
|---|---|---|
| P0 | Structured MIME editing | `mime.part(id)`, `part.headers.set/remove`, `part.params.set/remove`, `part.replace_body`, `part.remove`; stable part IDs, nested tree, duplicate-aware headers, correct encoding/boundaries, explicit signed/encrypted-content handling, original bytes retained |
| P0 | Complete inspection status | `inspection.complete()`, `inspection.errors()`, `inspection.limits()`; distinguish malformed, encrypted, skipped, truncated, unsupported and scanner-unavailable content; policy can defer/quarantine on incomplete inspection |
| P0 | Durable evidence capture | `journal(destination, original=True, envelope=True, required=True)`; original plus transformed hashes, original envelope/BCC, policy identity, scanner evidence, durable receipt and retry deduplication before acceptance |
| P0 | Retention and legal hold | `preserve(record_class, case_id, retain_until, legal_hold=True)`; authorized platform/storage adapter, immutable evidence receipt, release/deletion controls and external retention verification |
| P0 | Auditable policy decisions | `audit.event(reason_code, fields)` plus automatic evaluation records; policy/module digest, actor, message correlation, decisions, transformations and delivery receipt; protected independent checkpoints and SIEM export |
| P0 | Policy governance and isolation | Read-only `policy.identity()` / `tenant.id()`; host-enforced signed/versioned bundles, approvals, rollback, tenant grants and allowed monitoring destinations; enforce capabilities even if a script is malicious |
| P1 | Per-recipient decisions | `recipient.scope(address)` with scoped accept/divert/screen/quarantine; split plans without leaking one tenant's data, partial-delivery ambiguity or duplicate copies |
| P1 | Structured DLP and redaction | `dlp.findings(profile)`, `redact(findings)`, `classify(label)`; contextual/checksummed identifiers, exact-data matching, document fingerprints and explainable locations; `set_dlp` currently only requests host behavior |
| P1 | Deep attachment inspection | `archive.entries()`, `document.findings()`, `attachment.detected_type()`; recursive expansion with byte/ratio/depth/time limits, encrypted-container status, magic-byte/type mismatch detection, extracted text and macros |
| P1 | Content disarm and URL treatment | `sanitize_document(profile)`, `rewrite_urls(profile)`; preserve originals, rescan results, OCR/QR findings, sandbox receipts and a host-backed time-of-click service |
| P1 | Encryption/signature transformation | `encrypt_for(profile)`, `sign_with(profile)`, trusted decrypt capability; key isolation and explicit disposition for S/MIME/PGP; re-sign after authorized mutation where required |
| P1 | Recipient identity and information barriers | `directory.member_of`, `recipient.classification`, `information_barrier.check`; bounded trusted directory lookups and outbound/internal policy scope |
| P1 | Enterprise delivery operations | Read-only adapter health/capabilities; durable queues, HA/fencing, monitored retries, backpressure, reconciliation and backup/restore qualification supplied by host services |

Existing filtering is broader than these gaps: authentication verification,
header validation, URL extraction/display mismatch checks, attachment metadata
and extension checks, scoring/Bayes/ML, ClamAV/YARA integration and normalized
external analyzer findings already exist. OCR/QR, oletools, capa and sandbox
results can arrive through sidecars. That integration does not itself implement
native document extraction, recursive archive scanning or safe content rewriting.

## Reuse the platform's compliance capabilities

The companion platform already contains:

- `internal/compliance/engine.go`: envelope-domain rules for hold/reroute/copy/BCC,
  retention/legal-hold settings and principal/domain/action grants.
- `internal/storage/compliance.go`: journal-backed hold changes, protected release
  and retention-aware deletion.
- `internal/auditlog/audit.go`: verifiable hash-chained records, requiring an
  independently retained head to detect truncation/full rewriting.
- `cmd/mailhub-preserve` and `docs/DEPLOYMENT_QUALIFICATION.md`: Object Lock
  preservation with retention/hold/checksum verification and receipts.

These are integration gaps in MailScript, not a reason to rebuild the platform's
storage engine. The portable adapter should expose equivalent capabilities for
other MTAs and refuse unsupported required preservation plans. MailScript's
current adapter sends processed bytes and action strings; it needs a versioned
extension carrying original evidence, structured compliance requests and receipts.
An ordinary `screen_to()` mailbox copy is not that preservation contract.

## Regulatory scope

Select requirements by organization, jurisdiction and record class. For example,
SEC broker-dealer electronic recordkeeping requirements include a WORM or
audit-trail alternative; the latter must permit recreation of modified/deleted
original records. A BCC mailbox alone does not establish those properties.
See the [SEC electronic recordkeeping FAQ](https://www.sec.gov/rules-regulations/staff-guidance/trading-markets-frequently-asked-questions/rule-amendments-broker).

For applicable ePHI systems, the HIPAA Security Rule encompasses administrative,
physical and technical safeguards including access, audit, integrity and
transmission controls. Filtering functions cover only part of that scope.
See the [HHS Security Rule summary](https://www.hhs.gov/hipaa/for-professionals/security/laws-regulations/index.html).

Implementation order: structured message/inspection model; evidence and platform
adapter contract; policy governance; per-recipient plans; deep DLP/transformation.
Keep regression coverage for unmodified wire bytes, signed messages, malformed
MIME, required-recipient failures and retry behavior throughout.
